# Lentaro M2 — первая платная версия

Дата: 21.10.2026. Статус: WRITTEN_SPEC_REVIEW_PENDING; продуктовый код M2 не изменён.

Владелец в текущем чате утвердил состав первой платной версии и разрешил начать работу. Этот документ фиксирует утверждённые правила и предлагаемые технические решения для проверки перед implementation plan. Утверждение краткого дизайна не означает, что написанная позднее спецификация уже проверена владельцем.

## 1. Результат для пользователя и порядок поставки

Lentaro — сервис для действующих агентов по недвижимости: готовые редакционные тексты и изображения → личный выбор → календарь → публикация в собственные Telegram/MAX. Существующая редакция realty-editorial-v3 и её 11 ролей сохраняются.

Сначала завершить восстановление и выпустить существующую M1, передать владельцу рабочую ссылку и пройти пользовательскую приёмку. После этого реализовать M2: самостоятельную регистрацию, восстановление пароля и платный доступ. Исследование и дизайн M2 разрешены сейчас; прежний порядок M1 → Owner testing → M2 implementation сохраняется.

Полный M2 принят, когда новый пользователь самостоятельно регистрируется, оплачивает доступ, выбирает материал и получает публикацию; видит дату окончания, продлевает доступ вручную и сохраняет свои данные после окончания оплаты. Тесты, merged source и развёрнутая/принятая версия обозначаются отдельно.

## 2. Утверждённые коммерческие правила

| Параметр | Правило владельца |
|---|---|
| Продавец | Самозанятый в Российской Федерации |
| Цена | 1000 RUB за один календарный месяц; сумма счёта 100000 копеек |
| Пробный период | Отсутствует |
| Продление | Клиент сам оплачивает следующий месяц; автосписаний и сохранения карты для рекуррентов нет |
| Платёжный сервис | Robokassa, после подтверждения подключения конкретного магазина |
| Истечение доступа | Просмотр своих данных и продление доступны; новые публикации приостановлены |
| Сохранность | Материалы и история сохраняются; истечение оплаты не запускает удаление |
| Возобновление | Просроченные публикации требуют явного пересмотра пользователем |

Одного ADMIN ACTIVE/BLOCKED недостаточно для платного доступа. Административная блокировка, подтверждение email и оплаченный период — независимые условия. Успешная оплата не снимает административную блокировку.

Нет новых тарифных уровней, trial, скидок, квот, автопродления или бесплатных платных периодов. Политику хранения/удаления и юридические тексты нельзя выдавать за утверждённые только потому, что сохранение данных при истечении доступа согласовано.

## 3. Существующая реализация и границы изменений

Повторно использовать Next.js 16.3.4, PostgreSQL/Drizzle, server sessions/scrypt, текущие USER ownership guards, private media, durable receipts и существующие Redis/BullMQ scheduler/worker.

| Пользователь и сессия | db/schema.ts; lib/server/auth/{owner,session,access,password}.ts | Подтверждение email, reset tokens и отдельная проверка платного доступа |
| Приглашения/ADMIN | lib/server/auth/{invitations,user-management,admin}.ts | Сохранить; ACTIVE не становится подтверждением оплаты |

Добавить отдельные модули billing и account-recovery; не превращать общий auth guard в запрет всех GET/renew/cancel запросов. До реализации составить полный список write/handoff boundaries, включая прямые API, shared copy/swipe, batch, upload, retry и reconciliation. Скрытая кнопка не является защитой.

Вне M2: VK/Instagram, AI, смена хостинга, новая очередь, переписывание приложения, публичный каталог частных материалов, командные роли и автоматическая миграция production.

## 4. Регистрация и восстановление доступа

Регистрация использует email и пароль с ограничениями текущего invite-пути: 12–128 символов; пароли хешируются существующим scrypt. Email нормализуется одинаково для login/invite/signup; уникальность проверяется транзакционно без создания второго пользователя для существующего email. Настроенный OWNER_EMAIL зарезервирован независимо от наличия строки в users: публичный signup не создаёт для него аккаунт или token, сохраняя нейтральный ответ. Это сохраняет существующий ADMIN bootstrap и соответствует ограничениям invite-пути.

Новый USER подтверждает владение email по одноразовой ссылке, затем получает доступ к своему пустому кабинету и оплате. Неподтверждённый аккаунт не начинает публикации. Signup/reset endpoints возвращают нейтральный ответ без раскрытия наличия аккаунта; отдельно ограничивают запросы по IP и email.

Предлагаемые проверяемые параметры: криптографический token 32 bytes, в auth token records только SHA-256; email verification TTL 24 часа, password reset TTL 30 минут. Новый reset инвалидирует прежние reset tokens. Успешный reset атомарно меняет passwordHash, расходует token и отзывает все сессии через существующий sessionVersion. BLOCKED остаётся BLOCKED. Legacy ADMIN, пароль которого находится в server env, не меняется через публичный reset.

Ссылки строятся только от закреплённого публичного origin; произвольный Host/redirect не используется. Token не попадает в логи/аналитику и очищается из адресной строки после открытия формы. Тесты используют локальный mail sink; реальная отправка требует отдельно согласованного SMTP/провайдера, домена и секретов. Провайдер и расходы не выбираются автоматически.

Письма отправляет durable outbox после COMMIT. Восстанавливаемое содержимое ссылки в outbox хранится только в аутентифицированном AES-256-GCM envelope с отдельным server-only ACCOUNT_MAIL_ENCRYPTION_KEY; ключ VK не переиспользуется. Plaintext token возникает только в RAM при создании/отправке, не в DB/logs. При ротации/расходовании/истечении token соответствующие неотправленные сообщения инвалидируются; после подтверждённой передачи или истечения срока encrypted body удаляется, минимальный технический статус сохраняется. Неизвестный/повреждённый envelope останавливает отправку. Настройка нового ключа — отдельный secrets gate. Успешный запрос не обещает доставку письма; UI позволяет ограниченно запросить новое письмо и сохраняет понятное состояние при сбое транспорта.

## 5. Счёт и подтверждение оплаты

Авторизованный пользователь нажимает «Оплатить месяц — 1000 ₽». Сервер создаёт собственный счёт с userId, суммой 100000 копеек, RUB, неизменяемой версией тарифа, режимом TEST/LIVE и уникальным числовым InvId. Сумма и владелец не берутся из browser payload. Повторный запрос с тем же operationId возвращает тот же счёт; конкурентные клики не создают несколько активных checkout одного пользовательского intent.

Реквизиты карты вводятся на стороне Robokassa; приложение их не принимает. Merchant credentials существуют только на сервере. TEST и LIVE разделены; тестовый платёж не создаёт production entitlement. Первый rollout M2 по умолчанию не включает live payments.

Основной автоматический источник оплаченного доступа — серверное ResultURL с корректной подписью. Единственный recovery-источник — подтверждённый server-to-server статус конкретного счёта от официального Robokassa API: сверены shop/InvId/сумма/окружение и окончательный successful outcome; если API не позволяет доказать нужное соответствие, оставить pending. Оба источника вызывают одну транзакционную процедуру записи оплаты/периода с одной deduplication key. Просмотр оператором, browser payload, screenshot и ручной флаг paid не являются источниками доступа. Проверять подпись ResultURL по точным исходным строкам, выбранному в кабинете алгоритму и официальному составу параметров; неизвестная конфигурация отклоняется. SuccessURL — только страница результата, не команда активации.

После проверки подписи проверить существующий счёт, его окружение и сумму. Денежная строка разбирается без float: `1000`, `1000.00` и `1000.000000` обозначают одну сумму, дробная копейка/экспонента/отрицательное значение отклоняются. Исходную строку подписи не заменять нормализованной. Email плательщика и Shp-поля не меняют серверное соответствие InvId → userId. Ограничить размер body и длины полей, отклонять повторяющиеся критичные параметры и неизвестные подписанные пользовательские поля; подпись проверять сравнением постоянного времени после проверки формата/длины.

В одной DB-транзакции заблокировать счёт и entitlement пользователя, записать уникальную оплату и один оплаченный период. Повторное валидное уведомление возвращает `OK{InvId}` без второго продления. Если COMMIT произошёл, а HTTP-ответ потерялся, повтор получает тот же результат. До подтверждённого COMMIT успешный ACK не отправляется.

Переход на FailURL/закрытие вкладки не доказывает отмену платежа. При неопределённости показывать «Проверяем оплату»; не создавать новый платёж автоматически. Разбирательство по конкретному счёту использует проверенный серверный статус провайдера в разрешённом operational scope. Raw callback, пароль подписи, reset tokens и персональные данные не сохраняются в публичных логах.

Разные действительно оплаченные счета — разные месяцы; их конкурентная обработка сериализуется на одном entitlement. Произвольное повторение callback одного счёта не создаёт новый месяц.

## 6. Календарный период

Период имеет начало включительно и конец исключительно; проверка `now < paidThrough` выполняется на сервере. Все timestamps хранятся в UTC, календарное прибавление месяца и отображение даты выполняются в Europe/Moscow.

Начало нового месяца — max(DB confirmation time, конец уже оплаченного периода). Раннее продление сохраняет оставшееся время. Календарный месяц прибавляется к этому началу; если дня нет в следующем месяце, берётся последний день, время сохраняется. Примеры: 31.01.2027 12:00 → 28.02.2027 12:00; 31.01.2028 → 29.02.2028; 28.02.2027 → 28.03.2027. Месяц не равен фиксированным 30 дням. При задержанном подтверждении не отнимать у пользователя время до серверной активации.

Это точное техническое толкование утверждённого календарного месяца представлено для review; оно не должно меняться неявно в реализации.

## 7. Истечение доступа и отправки

Не менять ACTIVE на BLOCKED при окончании оплаты. USER продолжает входить и читать свои ранее созданные материалы/медиа, календарь, историю и платежи. Создание/редактирование контента, копирование новых редакционных материалов, новые расписания и provider sends требуют подтверждённого email, ACTIVE и оплаченного периода.

Даже без оплаты разрешены logout, password recovery, оплата, отмена ещё не начатой публикации, выключение/отключение подключения и другие существующие безопасные действия, прекращающие отправку. Состояния «не оплачен» и «заблокирован администратором» имеют разные сообщения. Полный новый редакционный каталог не выдаётся как бесплатный доступ; сохранённые личные материалы остаются доступны.

Worker проверяет entitlement на конечной границе допуска к отправке, используя тот же порядок блокировок user/account/publication, что существующий путь. Оплата, administrative block и handoff не должны обходить друг друга. Уже начатая при действующем доступе отправка может завершиться после окончания периода; её receipt/неопределённость сохраняются, повторная отправка не допускается.

Недопущенная из-за окончания оплаты публикация получает durable billing hold до освобождения claim. HOLD переживает restart/reconciliation/renewal и виден пользователю; его нельзя подменять provider AUTH/PERMANENT failure. Одного временного `now > paidThrough` недостаточно: после оплаты просроченная очередь иначе отправится автоматически.

После позднего продления прошлые SCHEDULED/QUEUED задания не отправляются пачкой. Каждая просроченная публикация проходит явный пересмотр сети/текста/времени пользователем; сохраняются исходный intent и receipts. Будущие задания вне истёкшего окна продолжаются только при валидном доступе и отсутствии собственного hold. Unknown/PUBLISHING не преобразуются в безопасно повторяемые задания.

## 8. Минимальная модель и интерфейс

Добавить additive schema для invoice/payment receipt, entitlement/периодов и durable publication billing hold; для регистрации/восстановления — token records и mail outbox. Точные таблицы/ограничения/интерфейсы фиксируются в implementation plans соответствующих самостоятельных частей. Не хранить оплату одним browser-флагом или одним полем ACTIVE.

В кабинете: цена/период, «Оплатить» или «Продлить», «Оплачено до …», «Ожидаем подтверждение», история своих счетов/оплат и причина приостановки отправки. Browser reload получает авторитетный серверный статус. Возврат с checkout не показывает доступ активным до ResultURL/проверенного серверного подтверждения.

ADMIN видит пользователей, состояние доступа, даты и агрегированные платёжные статусы; не получает доступ к частным неопубликованным материалам или секретам. Первая версия не содержит произвольного продления без оплаты и автоматического денежного возврата из админки. Спор/возврат/чек имеют отдельную operational процедуру с доказательством конкретной операции; до публичных продаж она обязательна.

Существующий ADMIN сохраняет техническое администрирование и своё ранее принятое owner publishing поведение. USER ACTIVE, старое приглашение или тестовый fixture не превращаются в оплаченный аккаунт. Конверсия существующих M1 USER и включение enforcement требуют отдельного release inventory/решения, чтобы source migration не отозвала доступ неожиданно.

## 9. Проверки и самостоятельные части

| Часть | Обязательные проверки |
|---|---|
| Account recovery | Конкурентные invite/signup, reserved OWNER_EMAIL до bootstrap, существующий email без enumeration, token expiry/reuse, одновременный reset, отзыв сессий, сохранение BLOCKED/ADMIN boundary, отказ SMTP и invalid envelope; отсутствие plaintext tokens в DB/logs |
| Billing core | Календарные края/високосный год/раннее продление, повтор одного intent и callback, callback/status-query race, две разные оплаты, неверная подпись/сумма/счёт/режим, COMMIT acknowledgement loss |
| Content/handoff enforcement | Прямые API и batch/swipe/upload, оплаченный A/неоплаченный B, ADMIN-as-non-owner, expiry на последней границе, уже начатая отправка, durable hold и restart |
| Browser/HTTP | Новый USER → оплата → own content → cancel/expiry/renew/review; reload и потерянный ответ; desktop/390/320; paid status не зависит от SuccessURL |
| Release | Exact source/image/ledger, isolated rehearsal, одна очередь/один sender, data preservation, тестовая интеграция, отдельный разрешённый live payment и USER provider scope |

Для каждого изменения: meaningful RED → минимальная реализация → GREEN → соответствующая регрессия → независимый Critic → exact-head CI. Исторические M1 проверки не повторять без source/base изменения или нового unresolved concern. Source tests не являются live acceptance.

Архитектурные части планировать отдельно: account recovery; billing/entitlement; применение допуска к существующему контенту и worker; UI/release acceptance. Между ними нужны явные интерфейсы. Это один утверждённый продуктовый результат, а не разрешение смешать весь код в один большой PR.

## 11. Внешние prerequisites и gates

До внешнего действия подготовить конкретный пакет, а не запрос «разрешить всё»: окружение, source/image, миграции, действия/число операций, сохранность данных, наблюдаемость отказа и совместимый rollback. Продолжать независимую разрешённую source-работу без согласований каждого файла.

Публичный коммерческий выпуск зависит от: принятой M1; восстановимости и согласованной production destination; подключения магазина Robokassa и Робочеки СМЗ; server-only credentials; согласованного email transport/public origin; оферты, цены/периода, контактов, privacy и процедуры возврата/аннулирования чека. Полные реквизиты и ключи собираются приватно и не публикуются в спецификации. Доступность провайдера не является подтверждением конкретного merchant onboarding.

Merge, staging/production release, persistent migrations, secrets/infra/DNS, SMTP/provider operations и реальные платежи/возвраты остаются отдельными точными gates. Этот этап не создаёт аккаунтов, не принимает договоры, не меняет env/БД и не отправляет писем/денег/публикаций.
