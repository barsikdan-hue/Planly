## 2. Что именно собираем

Lentaro — готовый к пользовательскому пилоту сервис для действующих агентов по недвижимости:

**Войти → подключить свой Telegram/MAX → открыть готовый контент → выбрать сети и расписание → свайпами заполнить календарь → получить публикации и увидеть результат.**

Существующая внешняя редакция `$realty-editorial-v3` из 11 ролей готовит общие тексты и изображения. Не пересоздавать редакцию, не обучать роли заново, не добавлять персональную AI-генерацию и платные AI API в приложение.

Ближайший измеримый результат — одна рабочая версия по ссылке, которую владелец и коллеги могут использовать целиком. Затем ошибки и неудобства исправляются по воспроизводимым пользовательским сообщениям. Технические проверки разработчики выполняют сами.

Это M1 — рабочая продуктовая версия по приглашениям. M2 — платный публичный запуск после решения владельца о цене, оплате и политике подписки. M1 не называть коммерчески завершённым SaaS: оплата пока не реализована. VK/Instagram — M3, не условие выпуска Telegram/MAX версии.

## 3. Один согласованный объём вместо десятков остановок

После согласования этого документа Codex получает единый implementation scope M1 и самостоятельно выполняет внутренние задачи A–F. Название/контракт каждой внутренней задачи и её проверки ведутся в рабочем ledger, но не требуют отдельного «одобряю» владельца для каждого файла, теста, дизайна или перехода между A–F.

В рамках M1 разрешаемый после согласования объём: inspect затронутого кода, подготовка конкретного плана, обычные локальные решения, реализация, additive migration source, изолированные тесты, исправление доказанных ошибок затронутого пути, документация, task branches, commit/push и Draft PR на источники. Существующие grants/WIP сохраняются. Это НЕ разрешение на main merge или изменение рабочих сред.

Использовать поэтапный план внутри одного рабочего цикла. Не заканчивать работу после каждого успешного теста вопросом «идём дальше?». Коротко сообщать достигнутый пользовательский результат, blocker и следующий шаг. Если один пункт заблокирован внешним доступом, продолжать другие независимые пункты M1.

При необходимости отдельного релиза подготовить конкретный reviewable release candidate, diff миграций, порядок rollout/rollback и одно понятное предложение владельцу. Запрос может перечислять несколько связанных действий, но каждое должно иметь точное окружение, SHA и границы. Не просить абстрактно «разрешить всё».

Вне scope M1: новые расходы/платные сервисы, самостоятельный перенос production, уничтожение/очистка данных, изменение DNS/секретов/доступов, реальные provider reads/sends без уже действующего точного согласия, массовое приглашение людей, тарифы/списания, VK/Instagram, CRM и сложные роли.

## 5. Минимальная техническая конструкция

Переиспользовать существующие `components/planner/{app,shared-library,swipe-planner,calendar,settings}.tsx`, `lib/server/shared-library.ts`, `posts.ts`, `publications.ts`, `swipe-feedback.ts`, `social-connections/`, `scheduler/`, `storage.ts`, `db/schema.ts` и B1 PR #68. Перед конкретной правкой читать соответствующие actual файлы/тесты. Имена новых функций/API/таблиц определить по inspect; перечисление файлов не является требованием трогать каждый из них.

Путь решения: shared original+revision → пользовательское намерение → независимый personal result → existing Post/PostTarget/publications → DB/queue/worker → подтверждённый исход по каждой сети. У copy и schedule уже есть отдельные receipts; продумать связывающую durable operation/provenance. Нельзя просто скрыть кнопку копирования, вызвать два независимых POST и забыть результат первого после сбоя второго. Восстановление должно находить прежний личный результат и прежнее намерение, а не плодить новые копии/публикации.

Зафиксировать серверную область дедупликации: пользователь, выбранный общий материал/ревизия и конкретное намерение. Два параллельных запроса одного намерения не создают два результата. Новый осознанный повтор уже использованного контента — отдельное действие, не автоматический retry.

Правила карточек:

- Вправо — одобрить этот материал в показанные собственные сети и показанный слот. Одно очевидное действие согласия; повторного ежедневного подтверждения нет.
- Влево — личный отказ; не меняет общий оригинал или решение другого агента.
- «Позже» — пропуск без публикации. Не создавать постоянную сложную preference-систему ради пропуска.
- Пока сервер не подтвердил решение, не показывать окончательный успех. При неизвестном исходе сохранять intent и предложить его восстановить.
- Нет слота/отключена сеть — показать исправимое состояние, не отправлять вместо этого «сейчас».
- Личные правки не меняют общий оригинал. Изменение/снятие оригинала не переписывает уже согласованные личные посты.

Server-side ownership и user lifecycle проверяются при чтении, записи и перед handoff. Независимые статусы Telegram/MAX сохраняются. Исход AMBIGUOUS_DELIVERY не приводит к слепому повтору. Использовать текущие PostTarget, cancellation, binding revision и signed-media механизмы; не строить второй backend.

## 6. Редакция и наполнение без нового AI сервиса

Следовать текущему `$realty-editorial-v3` и visual contract. Не исправлять исторические обложки массово; взять пригодный материал или подготовить новый небольшой выпуск с актуальными источниками. Не создавать дорогой месячный пакет до проверки первого пути загрузки.

Первый выпуск можно подготовить через уже доступные подписки/инструменты. Новые платные API и превышение согласованного бюджета не разрешены. Если инструмент/лимит недоступен — зафиксировать фактический результат, не подменять готовые изображения промптами и не останавливать source-разработку интерфейса.

Для пилота достаточно компактной подборки, позволяющей проверить выбор, отказ, календарь и результат. Число материалов не маркетинговое обещание; указывать реально готовое. Источники, происхождение изображений и QA можно сначала сохранить в небольшом sidecar-манифесте с устойчивыми идентификаторами: не добавлять десятки полей в core tables без необходимости. Отдельную рекомендательную модель, автопереобучение и обязательный feedback dashboard до первого выпуска не строить.

## 7. Проверки без лишних циклов

- Во время разработки запускать связанные tests и meaningful regression на затронутую границу. Текст/цвет/отступ не требуют собственного полного native-прогона до и после каждой правки.
- Auth, ownership, согласие, idempotency, миграции и worker paths требуют соответствующих security/race/rollback tests, даже если пользовательский симптом выглядит маленьким.
- Full native, обязательные typecheck/lint/build, self-host и browser smoke выполнять на законченных review/release-кандидатах и в требуемом CI. Не менять CI/скрывать tests/увеличивать retries или timeouts ради ускорения.
- Успешный результат точного неизменившегося дерева не повторять без новой причины. Изменение source/base, воспроизведённый сбой или существенная новая зависимость — повод актуализировать проверки.
- Два необходимых вида review: focused для рискованного изменения и финальный сквозной для M1. Не устраивать цепочку одинаковых полных аудитов после каждого исправленного отступа. Existing mandatory repo checks сохранить.
- Старый teardown timeout не объявлять исправленным новым зелёным запуском. Пока причина не доказана, не делать speculative refactor. Если повторится — ограниченная диагностика конкретной сигнатуры.
- Существующие provider successes владельца сохраняют свой scope. Live sends нужны для нового канала/нового USER пути и выбранных форматов, а не для каждого UI commit.

Технический критерий M1: два изолированных fixture USER, общая лента, личный отказ/одобрение, независимость данных, reload/lost response/concurrent swipe без дублей, корректный календарь/отмена и честные provider outcomes. Проверки реальных пользователей/каналов проводятся только после release и разрешения на точный scope; они не подменяются fixtures.

## 8. Единственная пользовательская приёмка M1

После разрешённого staging-выпуска дать владельцу ссылку и последовательность:

1. Войти в Lentaro и открыть готовые посты.
2. Проверить подключённые Telegram/MAX или пройти понятное подключение своего канала.
3. Выбрать сети и время, одобрить один материал свайпом; другой отклонить/пропустить.
4. Найти выбранный пост в календаре, проверить редактирование/отмену до отправки.
5. После согласованной публикации открыть результат или понятную ошибку каждой сети.

Владелец оценивает удобство и сообщает, что не получилось; не выполняет локальные команды, SQL или технический QA. Для подключения независимого коллеги может понадобиться только его собственное действие согласия у провайдера. Разработчики не обходят это действие от его имени.

Ошибка оформляется коротко: ожидалось / получилось / шаги / версия. Codex сам воспроизводит её, доказывает причину и исправляет в рамках M1. Косметику и безопасные UX-недочёты допустимо дорабатывать после первой передачи; утечки данных, потеря контента, неверный адресат и дубли отправки блокируют расширение доступа.

## 9. Данные и выпуск на имеющемся сервере

Целевой ближайший runtime — существующий VPS staging. Не «поднимать Render». Render сохраняется до самостоятельного решения о production cutover. Новую VPS/managed DB/платный worker не заказывать.

Перед изменением постоянной staging/production БД проверить актуальные baseline, migration ledger и действующий A1 contract/result. Не повторять 0012, не применять 0013/0014/0015 по числу ledger rows. Готовить совместимый план по фактически отсутствующим migrations и exact candidate tree.

Вопросы off-VM destination/keys и paused #64/#65 не возобновлять по собственной инициативе. Подготовить краткий конкретный остаток: что именно необходимо для безопасного выбранного rollout и какое прежнее разрешение уже действует. Если его нет — один пакетный запрос на нужные действия, а не последовательность запросов на команды. Разработка в изолированной среде продолжается независимо.

Не останавливать/менять работающие sender/worker/cron, webhooks, DNS и user data без соответствующего release scope. До cutover выяснить единственного активного sender для переносимых данных, сохранить исторические receipts и неизвестные исходы.

## 10. Платный запуск M2 и расширения M3

M2 начинается после передачи рабочей M1; source исследования M2 не мешают M1.
