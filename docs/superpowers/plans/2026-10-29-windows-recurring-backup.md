## Предлагаемый режим

- Назначение: C:/Users/EliteSochi/.codex/private/planly-backups/recurring/.
  Доступ только владельцу Windows; вне Git и синхронизируемых Documents.
- Windows Task Scheduler, ежедневно в 04:00 МСК; timezone компьютера сейчас
  Russian Standard Time. При смене timezone остановить настройку и пересогласовать.
- Запуск только в интерактивном сеансе владельца, без сохранения пароля,
  повышения прав или пробуждения ПК. При входе владельца проверить давность копии
  и выполнить один пропущенный запуск; не воспроизводить очередь всех пропусков.
- При выключенном ПК копирования нет. Интервал 24 часа — целевой, не гарантия
  сохранности последних суток. Утрата ПК вместе с VPS этим решением не покрывается.
- Сначала хранить все успешные копии без автоматического удаления. Проверенную
  копию 26 октября и старые серверные копии не изменять. При нехватке места
  завершаться ошибкой до остановки приложения; политику удаления согласовать отдельно.
- Показывать локальный статус: last_attempt, last_success, возраст копии,
  этап ошибки и exit code. Не менять last_success после неполного запуска.
  Уведомление Windows — без писем, Telegram и внешних сервисов; при отсутствии
  сеанса уведомление не гарантируется, состояние остаётся в локальном отчёте.

## Согласованность и защита работающего приложения

Существующий backup26_create.py — одноразовый скрипт с датой, именами контейнеров
и историческим env-путём. Его нельзя устанавливать как регулярную задачу.
Он останавливает web/worker и запускает их в finally; это не защита от гибели
процесса или разрыва соединения. Нужен отдельный серверный контроллер операции.

Перед запуском сверить активный Compose, реальные конфигурационные зависимости,
идентичности сервисов, свободное место, права и уже выполняющиеся операции.
Ввести локальную и серверную блокировки. При незавершённых публикациях операцию
пропускать с явным NEEDS_ATTENTION, без отмены, повторной отправки или изменения
расписания. Этот консервативный режим может не давать ежедневных копий при
постоянно заполненном календаре; до production нужен отдельно проверенный режим
резервирования при обычной нагрузке, без ослабления согласованности данных.

До любой остановки поставить независимую от SSH защиту запуска тех же web/worker.
Контроллер должен переживать закрытие клиента, фиксировать этапы, иметь ограничение
времени остановки и обязательно восстанавливать сервисы. При отказе подготовки
защиты не останавливать приложение. Проверять health и сохранность идентичностей;
при ошибке восстановления — критический статус, без следующего backup/redeploy.
PG, Redis и storage не останавливать. Никаких sender-запросов и миграций.

Копия: custom pg_dump, медиа, Compose/env/CA и необходимые конфигурационные файлы,
закрытые runtime-метаданные и manifest с размерами/SHA256. Redis-очередь не запускать
из восстановленной копии. Не печатать env, токены, строки БД или signed URLs.

Сначала закрытый уникальный серверный каталог, затем загрузка через SSH с
BatchMode/StrictHostKeyChecking и уже проверенными ключом/known_hosts в новый
локальный каталог .partial. Ограничить имена manifest и запретить выход из каталога,
симлинки и перезапись. Проверить все размеры/хеши и права, затем атомарно пометить
локальную копию COMPLETE. Обрыв загрузки не должен запускать новый dump автоматически;
допустимо продолжить перенос того же неизменяемого проверенного снимка.

  авария после остановки одного сервиса, отказ restart/health, повреждённый файл,
  path traversal, неполная копия и сохранность предыдущего last_success.
- [ ] На disposable runtime доказать ограниченное восстановление после принудительной
  гибели контроллера/SSH. До PASS не разрешать остановку staging из новой задачи.
- [ ] Независимый review безопасности и targeted regression; Draft PR, точный HEAD.
- [ ] Подготовить точное имя задачи, XML расписания, пути, source hash,
  команду отключения и серверный watchdog для отдельного инфраструктурного gate.
- [ ] После разрешения выполнить один контролируемый запуск, проверить сохранность

- [ ] Только после успешного ручного запуска включить утверждённое расписание;
  проверить пропущенный запуск и реальную видимость статуса ошибки.

## Критерии готовности

SOURCE_TESTED, TASK_INSTALLED, FIRST_BACKUP_VERIFIED и RESTORE_VERIFIED — отдельные
статусы. Наличие задачи или manifest не означает восстановимость. Дата последней
проверенной копии должна быть видна владельцу. Не объявлять production готовым
по этому документу. Ничего из предложенного режима ещё не установлено и не запущено.
