# Lentaro M2 Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Register and recover a verified USER without leaking account existence or weakening existing owner/invite/session rules.
**Architecture:** Reuse existing users/scrypt/sessionVersion and email advisory locks. Add token/verification records plus an encrypted transactional mail outbox; SMTP is an injected transport. Public enrollment defaults OFF until the whole M2 release.
**Tech Stack:** Existing stack plus Nodemailer10.1.7 with bundled types; Node>=22.13.0. No external mail/test account creation.
**Spec:** [Approved design§4,8–11](../specs/2026-10-21-lentaro-m2-commercial-design.md).

## Global Constraints

All [index constraints/interfaces/lock order](2026-10-21-lentaro-m2-index.md) apply. Password12–128 characters,32-byte tokens, verification TTL24h/reset TTL30m, auth records SHA256 only. Separate ACCOUNT_MAIL_ENCRYPTION_KEY; no plaintext token DB/logs. M1 acceptance and plan approval precede execution.

## Review Focus

1. Reserved OWNER_EMAIL before bootstrap → neutral response, no row/token/outbox (Task1).
2. Invite/signup/reset races → one identity; blocked stays blocked and reset revokes all sessions (Task2).
3. Link-prefetch/GET/Host injection → no consumption, fixed origin, no third-party referrer (Task2).
4. Outbox crash or unknown SMTP outcome → no blind resend; invalidated token is not sent (Task3).
5. Stored ciphertext copied to another user/message → AAD authentication failure, zero send (Task1; dispatcher denial Task3).
