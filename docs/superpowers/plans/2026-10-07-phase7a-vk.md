# Phase 7A VK Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox tracking. Owner explicitly authorized autonomous execution; no intermediate plan approval is required.

**Goal:** Add VK text/photo publishing through the existing independent target workflow with safe server-only rotating OAuth credentials.

**Architecture:** Extend the current connector/account contracts. AES-256-GCM credentials and encrypted PKCE intents live in PostgreSQL; account advisory serialization plus a durable UNCERTAIN marker prevents reuse of a rotated refresh after crash/persistence failure. No scheduler redesign.

**Tech Stack:** Existing Node/Next.js/PostgreSQL/Drizzle/pg/crypto, API 5.199 pinned schema baseline, official VK ID backend OAuth.

**Spec:** [Approved OAuth design](../specs/2026-10-07-vk-oauth-design.md); [official research](../../verification/2026-10-07-phase7a-vk-contract.md).

## Global Constraints

- No merge/deploy/live VK post; no real credentials in tests/chat/source/logs/DTOs.
- Static app credentials/encryption key remain server env; Telegram/MAX remain env-only.
- Video unsupported; preserve existing owner, upload, Library recovery and bounded retry semantics.
- No app-specific permission/live proof inferred from fixtures or green CI.

## Review Focus

- Crash or lost refresh response: durable UNCERTAIN prevents reuse, tested in Task 1.
- Owner switch/replayed callback/disconnect: exact owner/account/one-use binding, tested in Tasks 1 and 3.
- Returned upload URL or provider error echo: reject leakage/SSRF/redirects, tested in Task 2.
- Three providers with one failed delivery: independent receipts and statuses, tested in Task 3.
- Account/key/purpose substitution and missing credentials: fail closed before provider request, tested in Tasks 1 and 2.
