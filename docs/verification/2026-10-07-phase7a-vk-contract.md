## API observations, not an implementation design

- `wall.post` distinguishes a negative community `owner_id` and `from_group`; its response requires `post_id`. The wall identifier combines destination owner and returned ID; canonical wall links follow that identifier. No published receipt was obtained.
- The photo schema defines the upload-server/save methods and saved photo identifiers; attachment syntax includes `photo<owner_id>_<id>`. **No photo flow is designed or implemented while app-supported auth is unproven.**
- `video.save` / `video.get` also declare user tokens. Optional `processing` / `converting` fields do not establish a dependable READY contract by their absence. Video readiness, limits and permission eligibility remain unproven; no video support is claimed.
- `guid` is a string in the wall schema, without a declared deduplication window or same-result guarantee. It cannot justify automatic resend after unknown delivery. Preserve the existing Planly ambiguity boundary.
- [Official error schema](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/errors.json) distinguishes authorization (5/27/28), permission denial (7/15), per-second limiting (6), flood control (9), rate limit (29), internal error (10) and invalid parameters (100). Numeric app/method quotas and final Planly mappings are not selected here. CAPTCHA/validation or unknown publication outcome must not be treated as an unlimited temporary retry.

## Why implementation stops

The official user OAuth path is feasible for an approved app; fundamental API impossibility is **not** proven. However, its app-specific `wall` / `photos` write grant and community have not been established. Owner explicitly requires supported auth proof before designing photo publication.

There is also a concrete architecture decision: `AGENTS.md` restricts provider tokens to server environment configuration and prohibits PostgreSQL storage. The current VK ID flow rotates credentials. Restart-safe scheduled publication therefore requires a decision on durable server-only OAuth credential lifecycle; an in-memory token cache or static initial refresh env value cannot preserve the rotated pair through restart. This is an inference from the published rotation contract and existing project restriction, not a provider runtime failure. No vault, database credential columns, Render secret mutation or infrastructure workaround has been introduced.
